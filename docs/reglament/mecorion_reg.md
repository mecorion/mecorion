# Регламент PostgreSQL-разработки Mecorion

## 1. Общие положения

### 1.1. Назначение

Настоящий регламент устанавливает единые правила проектирования, именования, разработки, изменения и оптимизации PostgreSQL-объектов в проекте Mecorion.

Регламент распространяется на:
- таблицы;
- представления и витрины;
- функции;
- процедуры;
- ограничения;
- индексы;
- SQL-запросы;
- миграции;
- backend-сущности и API-модели в части согласованных имен данных.

### 1.2. Цели

Регламент предназначен для того, чтобы:
1. обеспечить единый и предсказуемый стиль разработки;
2. повысить читаемость SQL-кода;
3. уменьшить количество неоднозначных архитектурных решений;
4. снизить риск ошибок при изменении данных;
5. обеспечить контролируемую производительность;
6. упростить масштабирование Mecorion;
7. сделать структуру БД понятной любому разработчику проекта.

### 1.3. Общие принципы

1. Имена объектов должны однозначно отражать их назначение.
2. Одинаковые сущности должны именоваться одинаково во всех слоях системы.
3. Предпочтение отдаётся явному поведению вместо неявного.
4. Оптимизация должна основываться на измерениях.
5. Изменение данных должно выполняться контролируемо.
6. Каждый функциональный домен должен иметь определённую область владения данными.
7. Преждевременное усложнение архитектуры не допускается без подтверждённой необходимости.

# Глава 2. Именование объектов и данных

## 2.1. Дата и время

### 2.1.1. Формат

Поля даты и времени именуются по шаблону:

`<event><temporalType>`

Используются суффиксы:
- `Dt` — дата без времени;
- `Tm` — время без даты;
- `Dtm` — дата и время.

Примеры:

```text
createDt
createDtm
updateDtm
publishDtm
archiveDtm
subscriptionExpireDtm
```

### 2.1.2. Уточнение смысла

Если короткое имя неоднозначно, добавляется контекст.

Примеры:

```text
moderationStartDtm
moderationEndDtm
resolutionVoteEndDtm
subscriptionStartDtm
subscriptionEndDtm
```

### 2.1.3. Запрещённые альтернативы

Не используются разные стили для одного смысла:

```text
createdAt
creationDate
dateCreated
updatedAt
timestamp
```

### 2.1.4. Сквозное именование

Для одного значения по возможности сохраняется одно имя на всех уровнях:

```text
PostgreSQL -> Backend -> API -> Frontend

createDtm  -> createDtm -> createDtm -> createDtm
```

### 2.1.5. Часовые пояса

1. `Dtm`, обозначающий конкретный момент времени, хранится в UTC.
2. Часовой пояс применяется при отображении пользователю.
3. Исключение допускается только при необходимости соблюдать контракт внешней системы.

## 2.2. Наименование PostgreSQL-объектов

Используются следующие префиксы:

| Объект | Префикс | Пример |
|---|---|---|
| Таблица | `t` | `tPublication` |
| Представление / витрина | `v` | `vPublication` |
| Процедура | `prc` | `prcPublicationCreate` |
| Функция | `fnc` | `fncUserAccessCheck` |
| Primary Key | `pk` | `pkPublication` |
| Foreign Key | `fk` | `fkPublicationSpace` |
| Unique Constraint | `uq` | `uqUserEmail` |
| Check Constraint | `ck` | `ckSubscriptionPeriod` |
| Индекс | `ix` | `ixPublicationSpaceId` |

## 2.3. Ограничения

### 2.3.1. Общее правило

Все ограничения создаются явно через именованный `CONSTRAINT`.

Правило распространяется на:
- `PRIMARY KEY`;
- `FOREIGN KEY`;
- `UNIQUE`;
- `CHECK`.

Пример:

```sql
CONSTRAINT pkPublication
    PRIMARY KEY (id),

CONSTRAINT fkPublicationSpace
    FOREIGN KEY (spaceId)
    REFERENCES core.tSpace (id)
```

### 2.3.2. UNIQUE — `uq`

`UNIQUE` гарантирует, что значение или комбинация значений не повторяется.

Пример:

```sql
CONSTRAINT uqUserEmail
    UNIQUE (email)
```

Типичные сценарии:
- email;
- username;
- `code` справочника;
- внешний идентификатор;
- составной бизнес-ключ.

### 2.3.3. CHECK — `ck`

`CHECK` проверяет логическую корректность значения.

Пример:

```sql
CONSTRAINT ckSubscriptionPeriod
    CHECK (endDtm > startDtm)
```

Другие примеры:

```sql
CONSTRAINT ckRatingValue
    CHECK (ratingValue >= 0 AND ratingValue <= 5)
```

```sql
CONSTRAINT ckUserAge
    CHECK (age >= 0)
```

Разница:
- `UNIQUE` отвечает на вопрос: «Есть ли дубликат?»
- `CHECK` отвечает на вопрос: «Допустимо ли это значение?»

---

## 2.4. Алиасы

1. Алиас должен быть понятен без дополнительного поиска по запросу.
2. Не следует чрезмерно сокращать имена.

Предпочтительно:

```sql
auth.tSession AS session
clientcore.tUser AS user
core.tPublication AS publication
```

Не рекомендуется:

```sql
auth.tSession AS ses
core.tPublication AS p
```

Допустимы общепонятные сокращения:

```text
validation -> vld
source -> src
```

# Глава 3. Схемы и владение данными

## 3.1. Разделение по схемам

Каждая схема относится к определённому функциональному домену Mecorion.

Примеры:

```text
core
clientcore
auth
music
book
portalcore
```

Назначение:
- `core` — ядро платформы;
- `clientcore` — пользователи и общие пользовательские сущности;
- `auth` — идентификация, аутентификация, доступ, сессии и безопасность;
- `music` — музыкальный сервис;
- `book` — книжный сервис;
- `portalcore` — общие и переиспользуемые объекты портала.

## 3.2. Владение данными

1. Каждая таблица имеет одного функционального владельца.
2. Владельцем считается домен или сегмент, которому принадлежит схема.
3. Чужой домен не должен произвольно изменять внутренние таблицы другого домена.
4. Междоменное взаимодействие выполняется через согласованный контракт.
5. Это снижает связанность и упрощает перенос, масштабирование и изменение внутренней модели.

## 3.3. Auth

`auth` является общесистемным сегментом Mecorion.

Он отвечает за:
- идентификацию;
- аутентификацию;
- авторизацию;
- управление сессиями;
- доступ с нескольких устройств;
- безопасность аккаунта;
- обнаружение подозрительной активности;
- защиту от взлома и кражи аккаунта.

Другие сервисы используют Auth, но не должны зависеть от его внутренней структуры таблиц.

# Глава 4. Типы данных и структура колонок

## 4.1. Типы данных

Типы данных пишутся полностью и в верхнем регистре.

Используется:

```sql
INTEGER
BIGINT
BOOLEAN
VARCHAR
TEXT
NUMERIC
DATE
TIME
TIMESTAMP
TIMESTAMPTZ
```

Не используется:

```sql
INT
bigint
varchar
```

## 4.2. NULL

1. `NOT NULL` является вариантом по умолчанию.
2. `NULL` допускается только тогда, когда отсутствие значения имеет самостоятельный бизнес-смысл.
3. Nullable-поле должно быть логически обосновано.

## 4.3. Boolean-поля

Boolean-поля именуются в положительной форме.

Используется:

```text
isActive
isVerified
isDeleted
isVisible
```

Не рекомендуется:

```text
isNotActive
notVerified
isNotBlocked
```

## 4.4. Периоды

Используются симметричные названия:

```text
startDt
endDt

startDtm
endDtm
```

При необходимости добавляется контекст:

```text
subscriptionStartDtm
subscriptionEndDtm

moderationStartDtm
moderationEndDtm
```

# Глава 5. Справочники, статусы и системные коды

## 5.1. Структура справочника

Для статусов, типов, ролей и других системных классификаторов используются как минимум:
- `id` — внутренний идентификатор;
- `code` — стабильный программный код;
- `name` — человекочитаемое имя.

Пример:

```text
id | code  | name
1  | base  | Базовый пользователь
2  | agent | Агент
```

## 5.2. Поле code

`code`:
1. предназначен для разработчиков и программной логики;
2. не зависит от локализации;
3. должен быть уникальным в пределах справочника;
4. должен быть стабильным;
5. должен быть человекочитаемым;
6. не должен зависеть от `name`.

После ввода в эксплуатацию изменение `code` рассматривается как изменение программного контракта.

## 5.3. Магические значения

Не допускается бизнес-логика с необъяснимыми значениями.

Не рекомендуется:

```sql
WHERE publication.statusId = 3
```

Допустимо:

```sql
WHERE publication.statusId = @publishedStatusId
```

Значение может определяться через:
- enum;
- системную константу;
- справочник;
- стабильный `code`;
- иной централизованный источник.

Не требуется выполнять `JOIN` со справочником при каждом высоконагруженном запросе, если значение уже однозначно известно приложению.

# Глава 6. SQL-стиль и читаемость

## 6.1. SELECT

`SELECT *` запрещён.

Используется явное перечисление полей:

```sql
SELECT
    publication.id,
    publication.title,
    publication.createDtm
FROM core.tPublication AS publication
;
```

## 6.2. JOIN

Соединения выполняются только через явный `JOIN`.

Используется:

```sql
FROM clientcore.tUser AS user
INNER JOIN auth.tSession AS session
    ON session.userId = user.id
```

Не используется:

```sql
FROM clientcore.tUser AS user,
     auth.tSession AS session
WHERE session.userId = user.id
```

## 6.3. Форматирование

1. SQL-ключевые слова пишутся в верхнем регистре.
2. Поля крупных запросов располагаются по одному на строку.
3. Каждый `JOIN` оформляется отдельным блоком.
4. Условия `WHERE` располагаются по одному на строку.
5. `ORDER BY` оформляется отдельным блоком.

# Глава 7. Индексы

## 7.1. Назначение

Индекс создаётся для конкретного сценария доступа к данным.

Индекс может использоваться для ускорения:
- поиска;
- фильтрации;
- `JOIN`;
- сортировки;
- диапазонных условий;
- поиска зависимых строк;
- высокочастотных запросов.

Индекс не создаётся только потому, что колонка существует.

## 7.2. Наименование

Формат:

```text
ix<Table><Column...>
```

Примеры:

```text
ixTrackAlbumId
ixPublicationSpaceIdCreateDtm
ixSessionUserIdExpireDtm
```

## 7.3. Стоимость индекса

Каждый индекс:
1. занимает дисковое пространство;
2. занимает место в кэше;
3. увеличивает стоимость `INSERT`;
4. увеличивает стоимость `DELETE`;
5. может увеличивать стоимость `UPDATE`;
6. требует обслуживания PostgreSQL.

Поэтому лишние и дублирующие индексы не допускаются.

## 7.4. Индексы FOREIGN KEY

Наличие FK само по себе не является достаточной причиной для автоматического создания индекса.

Индекс создаётся, если FK участвует в:
- частых `JOIN`;
- фильтрации;
- поиске дочерних строк;
- удалении или изменении родительских записей;
- других значимых операциях.

## 7.5. Составные индексы

Составной индекс содержит несколько колонок.

Пример:

```sql
CREATE INDEX ixPublicationSpaceIdCreateDtm
    ON core.tPublication (
        spaceId,
        createDtm DESC
    )
;
```

Порядок колонок имеет значение.

## 7.6. Перед созданием индекса

Необходимо определить:
1. какой запрос индекс оптимизирует;
2. как часто выполняется запрос;
3. размер таблицы;
4. скорость роста таблицы;
5. поля `WHERE`;
6. поля `JOIN`;
7. поля `ORDER BY`;
8. существующие индексы;
9. частоту операций записи;
10. оправдана ли стоимость индекса.

## 7.7. Ревизия

Индексы периодически анализируются. Неиспользуемые и дублирующие индексы удаляются только после проверки их фактического назначения.

# Глава 8. SARGability и условия поиска

## 8.1. Принцип

Условия должны по возможности позволять PostgreSQL использовать индекс напрямую.

Не рекомендуется:

```sql
WHERE EXTRACT(YEAR FROM publication.createDtm) = 2026
```

Предпочтительно:

```sql
WHERE publication.createDtm >= @startDtm
    AND publication.createDtm < @endDtm
```

## 8.2. Когда правило особенно важно

SARGability обязательна к анализу, если:
1. таблица большая;
2. таблица быстро растёт;
3. запрос выполняется часто;
4. на поле есть или планируется индекс;
5. запрос обслуживает критичный API endpoint;
6. условие используется в batch-операции;
7. поле участвует в `JOIN`.

## 8.3. Допустимые отступления

Функция или вычисление допустимы, если:
1. таблица маленькая;
2. запрос редкий;
3. индекс не нужен;
4. используется подходящий функциональный индекс;
5. вычисление требуется бизнес-логикой;
6. execution plan и измерения показывают отсутствие проблемы.

# Глава 9. Вычисляемые данные и денормализация

## 9.1. Базовый принцип

Не хранится значение, которое можно дешёво и однозначно вычислить.

## 9.2. Когда денормализация допустима

Только если одновременно:
1. исходный расчёт дорогой;
2. значение используется часто;
3. проблема подтверждена измерениями;
4. есть измеримый выигрыш;
5. существует единый механизм обновления;
6. существует механизм пересчёта или восстановления;
7. индекс или более простой запрос не решают проблему.

## 9.3. Пример

Допустимо хранить:

```text
commentCount
ratingCount
ratingValue
```

если связанные данные исчисляются миллионами или миллиардами строк и постоянные `COUNT()` / `AVG()` становятся слишком дорогими.

# Глава 10. UPDATE и DELETE

## 10.1. Основной принцип

1. `UPDATE` и `DELETE` являются нормальной частью логики Mecorion.
2. Запрещены неконтролируемые изменения данных.
3. Каждый штатный запрос должен однозначно определять область изменения.

## 10.2. Штатный UPDATE

```sql
UPDATE core.tPublication
SET
    title = @title,
    updateDtm = @currentDtm
WHERE id = @publicationId
;
```

Требования:
1. условие соответствует бизнес-ключу или другому явно определённому набору строк;
2. разработчик понимает ожидаемое количество изменяемых строк;
3. если должна измениться одна строка, желательно проверять соответствующий результат;
4. массовое изменение должно иметь отдельный сценарий.

## 10.3. Штатный DELETE

```sql
DELETE FROM auth.tSession
WHERE id = @sessionId
;
```

Требования:
1. область удаления задаётся явно;
2. ожидаемый объём удаления понятен;
3. каскадное удаление проектируется осознанно;
4. для критичных сущностей заранее определяется physical delete или soft delete.

## 10.4. UPDATE/DELETE без WHERE

`UPDATE` и `DELETE` без `WHERE` запрещены для штатной логики приложения.

Они допустимы только при намеренной операции над всей таблицей:
- миграция;
- системный пересчёт;
- техническая очистка;
- административная операция;
- массовая подготовка данных;
- изменение модели данных.

## 10.5. Массовые операции

Перед массовой операцией необходимо:
1. определить ожидаемое количество строк;
2. проверить запрос на Dev/Test;
3. проверить корректность условий;
4. оценить блокировки;
5. оценить объём WAL;
6. оценить влияние на репликацию;
7. оценить время выполнения;
8. определить необходимость batch-обработки;
9. определить способ восстановления или отката;
10. проверить влияние на индексы;
11. определить безопасное окно выполнения, если операция тяжёлая.

## 10.6. Большие таблицы

Для миллионов и миллиардов строк следует рассматривать:
- batch-обработку;
- изменение диапазонами;
- изменение по ключу;
- паузы между пакетами;
- фоновые migration jobs;
- partition-aware операции;
- создание новой структуры с последующим переключением.

## 10.7. Dev и Production

1. Тестирование на Dev/Test обязательно.
2. Успешный тест на Dev не гарантирует одинакового поведения на Production.
3. На Production отдельно оцениваются объём данных, блокировки, WAL, нагрузка, время выполнения и влияние на пользователей.

---

# Глава 11. Транзакции

## 11.1. Назначение

Транзакция используется, когда несколько операций должны быть атомарными:

```text
либо выполняются все изменения,
либо не выполняется ни одно
```

## 11.2. Пример

Создание пользователя:

```text
tUser
tUserRole
tUserSettings
```

Если эти изменения составляют одну бизнес-операцию и находятся в одной БД, они могут выполняться в одной транзакции.

## 11.3. Требования

Транзакция:
1. относится к одной бизнес-операции;
2. должна быть короткой;
3. содержит только необходимые операции;
4. минимизирует время блокировок;
5. не используется без необходимости.

## 11.4. Что не выполняется внутри транзакции

Без необходимости внутри открытой транзакции не выполняются:
- HTTP-запросы;
- обращения к внешнему API;
- отправка email;
- внешние файловые операции;
- длительные вычисления;
- ожидание пользователя.

## 11.5. Один statement

Один самостоятельный `INSERT`, `UPDATE` или `DELETE` не обязан дополнительно помещаться в явную транзакцию: PostgreSQL выполняет отдельный statement атомарно.

## 11.6. Несколько БД

При распределении данных:
1. локальные ACID-транзакции используются внутри одного узла или шарда;
2. распределённые ACID-транзакции не являются базовым механизмом;
3. при необходимости применяются Outbox Pattern, события, идемпотентные обработчики, retries, eventual consistency, compensating operations или Saga.

Конкретное решение принимается по фактическому масштабу системы.

# Глава 12. Масштабирование хранения

## 12.1. Допустимые подходы

При росте данных могут использоваться:
- partitioning;
- sharding;
- несколько БД;
- read replicas;
- специализированные хранилища;
- аналитические хранилища.

## 12.2. Когда масштабировать

Механизмы масштабирования вводятся тогда, когда:
1. существующая архитектура перестаёт удовлетворять требованиям;
2. проблема подтверждается метриками;
3. понятен ключ разделения данных;
4. стоимость усложнения оправдана.

# Глава 13. Анализ производительности

## 13.1. Общий принцип

Оптимизация выполняется на основании фактических измерений.

## 13.2. Когда нужен execution plan

Анализ рекомендуется или обязателен для:
- больших таблиц;
- быстрорастущих таблиц;
- нескольких `JOIN`;
- тяжёлых агрегатов;
- сортировки больших наборов;
- массовых `UPDATE`;
- массовых `DELETE`;
- batch-операций;
- сложных составных индексов;
- критичных API endpoints;
- высокочастотных запросов;
- запросов с выявленной проблемой производительности.

## 13.3. Процесс оптимизации

1. Определить запрос.
2. Зафиксировать исходное время.
3. Зафиксировать объём данных.
4. Получить фактический execution plan.
5. Проверить тип Scan.
6. Проверить количество обработанных строк.
7. Проверить `Sort`.
8. Проверить алгоритмы `JOIN`.
9. Проверить использование индексов.
10. Сравнить Estimated Rows и Actual Rows.
11. Проверить I/O.
12. Проверить Loops.
13. Проверить использование памяти.
14. Изменить запрос, индекс или структуру данных.
15. Повторить тест.
16. Сравнить показатели.

## 13.4. Основные показатели

Следует анализировать:

```text
Sequential Scan
Index Scan
Bitmap Scan
Sort
Nested Loop
Hash Join
Merge Join
Estimated Rows
Actual Rows
Rows Removed by Filter
Loops
Execution Time
Buffers
I/O
Temporary Files
Memory
```

# Глава 14. Контроль качества изменений БД

## 14.1. Перед созданием объекта

Проверить:
1. схему;
2. имя;
3. типы данных;
4. `NULL` / `NOT NULL`;
5. ограничения;
6. необходимость индексов;
7. владельца данных;
8. предполагаемый рост.

## 14.2. Перед изменением таблицы

Оценить:
1. количество строк;
2. блокировки;
3. влияние на индексы;
4. стоимость изменения;
5. WAL;
6. репликацию;
7. обратную совместимость;
8. миграцию данных;
9. возможность отката.

## 14.3. Перед Production

1. Изменения проверяются на Dev/Test.
2. Тяжёлые изменения дополнительно проверяются на объёмах, близких к Production.
3. Потенциально опасные операции имеют сценарий восстановления.
4. Изменения применяются воспроизводимо через миграции или другой контролируемый процесс.

# Глава 15. Обязательный чек-лист

Перед добавлением или изменением SQL-кода проверить:

1. Объект находится в правильной схеме.
2. Имя соответствует стандарту Mecorion.
3. Даты используют `Dt`, `Tm`, `Dtm`.
4. Типы данных написаны полностью и в верхнем регистре.
5. Все ограничения имеют явные имена.
6. `UNIQUE` используется для защиты от дубликатов.
7. `CHECK` используется для проверки допустимости данных.
8. Нет `SELECT *`.
9. Используются явные `JOIN`.
10. Алиасы понятны.
11. `NULL` используется только осознанно.
12. Boolean-поля имеют положительное имя.
13. Справочники имеют `id`, `code`, `name`.
14. Нет необъяснимых магических значений.
15. Индекс создаётся под конкретный сценарий.
16. Для составного индекса обоснован порядок колонок.
17. Нет лишних и дублирующих индексов.
18. Условия не мешают использованию индексов без необходимости.
19. Денормализация подтверждена измерениями.
20. `UPDATE` и `DELETE` имеют контролируемую область изменения.
21. Массовые операции проверены отдельно.
22. Транзакция используется только при необходимости атомарности.
23. Междоменные границы не нарушены.
24. Для тяжёлого запроса проверен execution plan.
25. Production-изменение имеет понятный сценарий применения и восстановления.

# Статус документа

Настоящая редакция является базовым утверждённым регламентом PostgreSQL-разработки Mecorion.

Регламент дополняется по мере появления новых архитектурных решений, требований к эксплуатации, производительности и масштабированию. Новые правила не должны противоречить уже утверждённым положениям без явного пересмотра соответствующей главы.
