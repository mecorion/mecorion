# Архитектурный контракт Mecorion DB 1.0

## 1. Физическая модель

На первом этапе используется одна PostgreSQL-база `mecorion`. Предметные
границы представлены схемами. Сервис и база данных не считаются синонимами.
Выделение отдельной БД выполняется только ради безопасности, независимой
доступности, масштаба или отдельного жизненного цикла.

## 2. Ответственность текущих схем

| Схема | Владелец данных |
|---|---|
| `core` | Сервисы, глобальные ресурсы, языки, территории, outbox |
| `account` | Аккаунты, профили, связь аккаунта с подтверждённым человеком, удаление |
| `auth` | Идентификаторы входа, credentials, устройства, сессии, challenges |
| `access` | Permissions, роли, scopes и назначения ролей |
| `content` | Канонический каталог, публикации, участники и дедупликация |
| `media` | S3-объекты, assets, варианты файлов, загрузка и транскодирование |
| `workflow` | Заявки, revisions, reviews и история состояний |
| `moderation` | Жалобы, ограничения permissions и апелляции |
| `legal` | Правовые статусы, лицензии, takedown и версии соглашений |
| `library` | Коллекции, избранное, прогресс и offline grants |
| `music` | Музыкальные расширения общего контента |
| `video` | Видеорасширения, иерархии, редакции и дорожки |
| `audit` | Неизменяемые события безопасности и управления |

Подробная карта владельцев и запретов находится в `docs/schema-map.md`.

## 3. Идентификаторы

Каждая основная сущность имеет:

- `id BIGINT` — компактный внутренний первичный ключ;
- `publicId UUID` — стабильный идентификатор API и будущего межсервисного обмена.

Клиенты не должны получать внутренние `id`. При физическом разделении БД
межсервисные ссылки сохраняются через `publicId`.

## 4. Единая модель ресурса

Объекты, к которым применимы общие функции платформы, регистрируются в
`core.tResource`. Доменные таблицы затем ссылаются на ресурс. Это позволит
избранному, коллекциям, комментариям, жалобам, правам и аудиту использовать
один стабильный идентификатор.

`core.tResource` не хранит доменные атрибуты трека, фильма, книги или файла.

## 5. Аккаунт и человек — разные сущности

`account.tAccount` представляет учётную запись. `account.tPersonAnchor`
представляет подтверждённого уникального человека без обязательного хранения
его открытых персональных данных.

Один человек может быть связан с историческими или восстановленными
аккаунтами, но уникальный индекс допускает только одну активную управляющую
eligibility. Это предотвращает повторное голосование и получение Agent,
Keeper или Moderator через новый аккаунт.

После удаления аккаунта:

1. вход и активные сессии прекращаются;
2. профиль и идентификаторы входа обезличиваются или удаляются;
3. контент может остаться под обезличенным авторством;
4. минимальное доказательство уникальности хранится до `retainUntilDtm`;
5. по окончании срока encrypted payload и digest подлежат уничтожению.

Приложение должно формировать `evidenceDigest` как keyed HMAC. Обычный хеш
email, телефона или документа использовать запрещено: его можно перебрать.
Ключ HMAC/шифрования хранится вне PostgreSQL, например в KMS/secret manager.

## 6. Auth и единый вход

Auth является единственным владельцем credentials и refresh-токенов.
Остальные сервисы получают короткоживущий access token с `sessionPublicId`,
`accountPublicId`, audience и permissions/scopes.

- PostgreSQL хранит долговечное состояние сессии.
- Redis содержит горячий кэш сессий, OTP, rate limits и locks.
- В БД записываются только хеши refresh-токенов, OTP, recovery seed и паролей.
- Каждый refresh token одноразовый и входит в rotation family.
- Повторное применение использованного токена должно отзывать всю family.
- Завершение одной сессии не завершает остальные сессии пользователя.
- Завершение всех сессий выполняется отдельной командой Auth.

## 7. Roles, permissions и scopes

Роль — именованный набор permissions. Назначение роли всегда содержит scope.
Scope может быть глобальным, сервисным или связанным с `core.tResource`.

Системные и общественные роли используют одну модель:

- `BASE` — базовые пользовательские возможности;
- `AGENT`, `KEEPER`, `MODERATOR` — управление сообществом;
- `SPONSOR` — entitlement-роль;
- `DEVELOPER`, `ADMIN`, `OWNER` — системные роли.

Проверка доступа выполняется по permission, а не по имени роли. Нельзя писать
условия наподобие `if role = 'ADMIN'` в доменной логике.

Назначение управляющей роли требует активной
`account.tGovernanceEligibility`. Инвариант защищён функцией
`access.fncValidateRoleAssignment`; в прикладной реализации назначение также
будет выполняться транзакционной процедурой и сопровождаться аудитом.

## 8. История и удаление

Состояния, важные для безопасности, сопровождаются append-only историей.
Обычные таблицы могут обновлять `updateDtm`, но история статусов не
перезаписывается.

Hard delete допустим для одноразовых технических данных после срока хранения.
Аккаунты, назначения ролей, сессии и управляющие решения отзываются статусом и
датой.

## 9. Межсхемные зависимости

В одной БД применяются внешние ключи. Они защищают целостность и не отменяются
ради гипотетического перехода к микросервисам.

Запрещаются:

- бизнес-триггеры, изменяющие сразу несколько предметных схем;
- запись модулем в таблицы чужой схемы;
- прямое чтение auth-секретов другими модулями;
- использование JSONB вместо нормальных связей и обязательных колонок.

`JSONB` допускается для криптографических параметров, метаданных клиента,
payload интеграционного события и редких расширяемых атрибутов.

## 10. Подготовка к разделению БД

- миграции разделены по владельцам данных;
- наружу выдаются UUID;
- события создаются через transactional outbox;
- обработчики обязаны поддерживать идемпотентность;
- межсхемные FK считаются документированными зависимостями;
- VPN-ноды не получают доступ к основной БД;
- Billing и VPN Control являются первыми кандидатами на отдельные БД.
